There are two viable directions for Top-K.

Option 1 is an exact sliding window: store records in time buckets, maintain a min-heap of capacity 100 per bucket, and merge active buckets on query. Writes are O(log 100). Memory has a clear upper bound, but late events, bucket rotation, and score ties need handling; if it depends on a database or disk-backed external state, I/O and operations cost are higher.

Option 2 is a Space-Saving approximate sketch: writes and memory are more stable and implementation complexity is lower, but results allow error. If the product must return exact records, recommend the exact option; if quantifiable error is acceptable and throughput comes first, the approximate option is better.

Before continuing to implementation, you need to decide whether the result semantics allow approximation error.
