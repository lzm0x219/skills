# 任务与环境验收

先遵循入口的配置审查与信任边界；以下检查不授权信任新目录或执行未审查的任务。精确命令和属性以实际 mise 版本支持的官方说明为准。

## 配置与工作目录

从发生故障的同一目录、同一环境选择和同一启动入口核对实际加载的配置列表、当前工具版本、可执行路径与任务工作目录。项目根配置只是一个来源，父目录、局部覆盖、环境选择和调用进程也可能影响结果。使用 [Configuration](https://mise.jdx.dev/configuration.html) 指引定位来源，不通过修改全局默认值掩盖项目问题。

在受影响任务中验证非敏感版本、路径和退出状态。确认相对输入／输出路径按预期目录解析，monorepo 的任务匹配只涵盖指定子项目。日志仅记录需要的环境变量名、是否存在及非敏感值；不导出整份环境作诊断附件。

## 依赖与执行顺序

`depends` 声明前置任务集合，列表顺序不构成串行保证。只有互不读写彼此产物的分支才适合并行。生成代码后再测试、格式化后再 lint 等有真实先后关系的任务，应建立显式依赖边，或使用当前版本支持的顺序执行步骤。共享输出目录、lockfile 或生成文件也需要明确唯一写入者。

审阅入口到叶子命令的完整路径：只读依赖图可能漏掉 `run` 中调用的任务。检查循环、遗漏步骤、错误被忽略或 shell 尾部成功命令掩盖失败。验证时故意让一个前置步骤失败，确认依赖它的步骤不执行、顶层入口返回非零；另测成功顺序。参见 [Task Configuration](https://mise.jdx.dev/tasks/task-configuration.html) 的 `depends` 和 `run`。

## 跳过、缓存与成功证据

先区分任务实际执行成功、freshness 跳过、缓存恢复、因平台／条件跳过，以及未运行。旧输出存在或日志重放都不证明本轮执行了测试。

为 `sources`／`outputs` 声明会改变结果的源码、配置、lockfiles 和生成输入；工具版本、环境及外部状态是否纳入缓存也须核查。没有可靠输入边界时，优先让正确性检查实际执行。使用 [Task Configuration](https://mise.jdx.dev/tasks/task-configuration.html) 的 freshness 规则，并按需转到 [Task caching](https://mise.jdx.dev/tasks/caching.html)。

用一次输入变化、一次输出缺失及一次失败运行验证命中／失效行为。已有产物不能被失败结果更新为成功缓存。需要本轮执行证据时，用当前版本支持的强制执行方式针对该任务重跑；保留无关全局缓存，不把清空缓存作为通用修复。

`mise tasks validate` 通过只证明它覆盖的静态规则；最后仍需原始入口下的真实项目命令和对应产物。未运行的 CI、IDE、shell 或平台不得标记可用。
