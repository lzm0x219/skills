# 宿主接入与恢复

首次接入、缺少验证器或恢复失败时读取。状态维护与外部动作派发是两个独立能力；接入流程不能扩大用户授权。

## 先选择所需能力

| 当前任务                           | 接入要求                                                                   |
| ---------------------------------- | -------------------------------------------------------------------------- |
| 仅说明或规划                       | 描述协议；不运行 CLI，因为 `show`、`verify` 也可能重建 snapshot            |
| 保存研究、代码修改或测试的当前状态 | 使用 `init`、局部补丁和 `show`／`verify`；这些状态操作不要求授权验证器     |
| 无副作用协议演练                   | 在临时目录使用 `reference-only`，只能记录模拟动作与模拟回执                |
| 真实发布或其他外部动作             | 已有用户授权、宿主固定验证器、明确的派发器、权威查询／回执和幂等或对账机制 |

缺少真实动作能力时，仅阻塞对应的外部动作，继续已授权的状态维护与准备。不能因缺少验证器而为普通研究记录反复请求授权。

## 可运行的本地演练

从仓库根目录运行；安装后的 Skill 使用实际安装目录中的同名脚本：

```sh
python3 skills/development/workflows/durable-execution-state/scripts/rehearse_recovery.py --steps 100
```

脚本仅使用标准库和公开 `statectl.py` CLI，在自动清理的临时目录内运行：

1. 连续更新同一计划值，记录序列化状态大小与 CLI 耗时。
2. 在补丁提交前注入失败，核对旧版本和旧值未改变。
3. 在动作登记提交后注入失败，删除模拟 snapshot，再从 SQLite 恢复；同一幂等键登记返回原 action ID。
4. 写入临时模拟服务账本并观察它；在回执提交后注入失败，再用同一回执重试，版本与事件数不重复增长。
5. 核验模拟证据后完成演练，运行重放和一致性验证。

这里的故障注入是事务边界的受控异常，不是机器断电测试。输出的 `real_external_actions=0`、`host_trust_verified=false` 明确证据范围。CLI 时间包含 Python 启动，状态字节数不是进程内存；演练不测模型 token 或真实长程任务成功率。模拟证据随临时目录清理，不作为生产证据留存。

## 真实验证器接入示例

[approval_file_verifier.py](../scripts/approval_file_verifier.py) 是可运行的精确请求验证器示例。它只接受宿主预先批准的完整请求 hash、授权引用和有效期，不执行任何业务动作，也不把输入中的自称授权当作批准。

宿主在模型不可写的目录中部署并固定程序、Python 解释器、启动 wrapper 和批准文件。`statectl.py` 只调用一个无参数的绝对路径，因此由宿主 wrapper 固定参数，例如：

```sh
#!/bin/sh
exec /usr/bin/python3 /opt/agent-host/approval_file_verifier.py \
  --approval-file /opt/agent-host/approvals/current.json
```

上述路径是接入示意，需由宿主按实际环境配置；不能由 Agent 在仓库中生成 wrapper 后自行认定可信。当前 Skill 目录中的示例代码本身也不是信任根。

批准文件格式如下。**宿主在取得真实批准后生成**，hash 由宿主对批准时的完整 action 请求按 UTF-8、key 排序、无额外空白 JSON 计算 SHA-256；包括 `idempotency_key`、`tool`、`args`、`authorization_ref` 和 `preconditions`，不能只 hash 工具名或参数。

```json
{
  "authorized": true,
  "authorization_ref": "approval://release-1",
  "request_sha256": "<宿主计算的完整请求 SHA-256>",
  "verifier_ref": "host-policy://release/v1",
  "expires_at": "<宿主指定的未来 UTC 时间，YYYY-MM-DDTHH:MM:SSZ>"
}
```

示例在缺失文件、畸形字段、请求不匹配或过期时退出 1，写入简短 stderr；成功时返回协议所需 JSON。验证器不能简单回显调用方的 hash 并始终返回 `authorized=true`。适用的示例测试仅使用临时批准文件，不证明真实宿主的权限隔离。

验证通过只登记意图。派发器仍需按 [状态转换协议](transition-protocol.md) 处理动作和回执，并在真正派发前核对批准仍适用、请求未改变；撤销授权或过期的意图不能仅凭曾经登记成功继续执行。

## 恢复决策

| 观察结果                          | 下一步                                                                             |
| --------------------------------- | ---------------------------------------------------------------------------------- |
| 补丁返回失败、版本未增加          | 根据当前状态重算；确认提交前失败后再做有界重试                                     |
| 补丁返回失败、版本已增加          | 核对目标路径与证据是否已有预期值；结果已提交时不重复应用                           |
| `begin-action` 返回 `reused=true` | 复用登记，不代表可以再执行。pending 先查询实际结果；confirmed／failed 复用终态回执 |
| 已登记，但不知道请求是否派发      | 使用同一幂等键向权威系统对账；没有可靠查询或去重能力时保持 pending 并升级          |
| 回执为 partial／unknown           | 记录已观察到的局部结果，继续保留 pending；补偿是单独动作，需有对应授权             |
| snapshot 缺失或损坏               | 从 SQLite 运行 `show`／`verify` 重建；不手改数据库或把旧 snapshot 写回             |
| 事件重放与数据库不一致            | 停止依赖该状态的写入，保留证据诊断；不要用“修复快照”掩盖账本不一致                 |

`verify` 成功仅说明内部一致，不证明 Git HEAD、文件内容、测试或远端对象仍然有效。完成前仍需重新访问对应事实源。

状态模型中的目标、完成条件与约束由初始化固定。新请求实质改变这些边界时，先保留旧任务的 pending 与证据，明确交接后初始化一个关联的新任务；不能直接编辑数据库绕过保护，也不能把未解决旧动作当作已完成。
